# SatyaDrishti Competitive Analysis

**Prepared:** 3 October 2026  
**Scope:** SatyaDrishti workspace compared with the 30 repositories supplied for SIH26034.

## Executive Summary

SatyaDrishti is one of the broadest product concepts in this group. Its differentiator is not just label OCR: it combines image scanning, a deterministic rule engine, regulatory retrieval, marketplace inspection, complaint intake, officer workflows, analytics, reporting, and email dispatch. Most listed projects focus on one inspection pipeline; only a few attempt a broader enforcement or consumer platform.

The important qualification is that breadth is not the same as dependable, production-grade behavior. Source review found several gaps between the product narrative and the evidence the implementation can currently support: font height is estimated from an assumed 180 mm image height rather than calibrated physical scale; contrast analysis fabricates a default 4.8:1 result when sampling fails; OCR-missing fields can become failures instead of “unable to verify”; the local report hash is simulated while displayed as a verified SHA-256/RSA signature; and the login is a client-side demo with no server-side authorization. The service worker caches the app shell but does not provide an offline inspection queue and later sync.

**Bottom line:** SatyaDrishti leads on platform breadth and integrated workflows. The most valuable next step is to make its inspection decisions and reports more defensible, not to add more dashboard features. Hakam’s rule/evidence controls, iTej’s calibrated-measurement discipline, NiyamDrishti’s offline evidence workflow, and Harsh’s evidence-coverage semantics are the most useful patterns to study.

## What SatyaDrishti Does Well

- **Full enforcement-oriented product surface:** inspector dashboards, products and manufacturer views, violation ledger, consumer complaints, case dossiers, regulatory settings, and analytics are represented in the app, rather than just a single upload form. Relevant entry points include [OverviewDashboard.tsx](../src/pages/dashboard/OverviewDashboard.tsx), [ViolationsLedger.tsx](../src/pages/dashboard/ViolationsLedger.tsx), [ConsumerComplaintsPortal.tsx](../src/pages/dashboard/ConsumerComplaintsPortal.tsx), and [ManufacturerRiskRanking.tsx](../src/pages/dashboard/ManufacturerRiskRanking.tsx).
- **A substantial OCR evidence pipeline:** [ocrService.ts](../src/lib/ocrService.ts) runs multiple English Tesseract preprocessing passes, retains OCR confidence and bounding boxes, aggregates lines across passes, and can call backend optical preprocessing and hybrid image/text extraction. The pull adds [barcodeService.ts](../src/lib/barcodeService.ts), which attempts ZXing decoding across rotations and selected crops. [OCRResultsPanel.tsx](../src/components/scanner/OCRResultsPanel.tsx) connects extracted fields back to image regions.
- **Improved extraction and capture handling in the latest pull:** backend prompt/regex changes target noisy MRP, USP, batch/date, and address text; OpenCV cropping now uses wider margins and guards against over-cropping curved packages. The backend contains Indic-script statutory patterns and an optional mBERT path, but the transformer is disabled by default and the browser OCR now uses English only. End-to-end Indic-language extraction should therefore be treated as unverified, not as supported just because multilingual parsing code exists.
- **Multi-evidence complaint intake:** [complaintOcrPipeline.ts](../src/lib/complaintOcrPipeline.ts) processes packaging, receipts/invoices, and other evidence, annotates copies while preserving originals, uploads evidence, and consolidates multiple views. This makes the consumer workflow richer than most scanners in the list.
- **A deterministic compliance layer plus regulatory context:** [ruleEngineService.ts](../src/lib/ruleEngineService.ts) evaluates statutory checks, while [ragKnowledgeService.ts](../src/lib/ragKnowledgeService.ts) provides regulatory retrieval. The backend also has a rule-version resolver in [rule_versioning.py](../backend/services/rule_versioning.py) and a separate validation augmentor in [llm_validation_service.py](../backend/services/llm_validation_service.py).
- **E-commerce surveillance is a real product differentiator:** [ecommerce_crawler_service.py](../backend/services/ecommerce_crawler_service.py) and [crawler_api.py](../backend/api/routes/crawler_api.py) implement scheduled and on-demand listing inspection, live-fetch fallbacks, history/log endpoints, persistence, and draft notices. Most competitors in the list do not implement a scheduled multi-marketplace crawler.
- **Reports and operational handoff:** [reportService.ts](../src/lib/reportService.ts) and [reportExporter.ts](../src/lib/reportExporter.ts) support single-product and session reports, PDF/DOCX output, OCR evidence, rule findings, and recommended actions. Email dispatch has a backend API and a demo fallback in [gmailService.ts](../src/services/gmailService.ts).
- **Mobile/PWA foundations:** camera capture, responsive views, manifest, and a service worker are present. These are a useful base for field use, even though the current offline behavior is not yet an offline inspection workflow.

## Recommended Improvement Roadmap

### P0: Make every finding honest

1. Replace “not detected = violation” with distinct `PASS`, `FAIL`, `REVIEW/UNABLE_TO_VERIFY`, and `NOT_APPLICABLE` states. A missing OCR hit is not proof that the physical label omits the declaration. Keep extraction confidence separate from rule outcome.
2. Remove fabricated optical fallbacks. If a contrast sample fails or a bbox is invalid, return an unavailable measurement and require review. Never substitute a plausible score.
3. Remove or isolate the muesli special-case scan path and fixed result counters. Real uploaded images must not inherit fixture declarations or hard-coded counts. Keep named demo scenarios behind an unmistakable demo mode.
4. Fix physical font checks: require a calibration card, measured panel dimensions, or another explicitly validated scale source; report calibration quality and uncertainty; return indeterminate when calibration is missing or unreliable. Use the law’s applicable table and package/category context, not a generic assumed package height.
5. Add an image-quality preflight for blur, glare, crop completeness, and readable resolution. Offer recapture guidance before a low-quality scan becomes a legal finding.

### P0: Make the app safe to present as an enforcement tool

6. Replace local email-based demo login with backend authentication and server-enforced roles. Restrict CORS to known origins, protect complaint/product/rule/report routes, and remove default/demo credentials from any shared deployment.
7. Replace the simulated report hash and “RSA-2048” label with a real SHA-256 digest over the exact source/evidence/report bytes, then sign with a real managed key if digital signatures are required. Add independent verification and tamper tests. Until then, describe the report as a generated screening report, not as signed or certified evidence.
8. Add a mandatory officer review gate before findings become notices or enforcement actions. Store who corrected a field, the before/after values, reason, evidence, rule-pack version, and timestamp. Keep draft notice creation clearly separate from legal issuance.

### P1: Establish legal and data provenance

9. Make a single versioned rule-pack artifact the source of truth for both frontend and backend. Every rule should include verified source/citation, effective dates, category/market applicability, conditional logic, severity, and reviewer approval. Record the pack version and evaluation date on every scan. Add a visible pending-review state for unverified citations.
10. Store OCR observations separately from normalized fields, model/engine version, source bbox, confidence, and extraction method. Every check should point to its supporting evidence or explicitly say why no evidence exists. Do not convert a barcode decoder's fixed confidence into a quality probability; validate checksum and registry identity as separate steps.
11. For crawler records, store the fetched page or a normalized snapshot, response status, retrieval time, exact source URL, parse confidence, and provenance per field. Label catalog/demo fallback records as synthetic. Confirm that parsed live content, not just defaults, feeds the audit before presenting crawler results as live surveillance.

### P1: Make field work resilient and testable

12. Add a real offline queue in IndexedDB with image retention, rule-pack snapshot, pending/synced/failed states, retries, idempotency, conflict resolution, and an explicit sync action. Keep offline OCR provisional; calculate the authoritative legal outcome on the server after sync.
13. Build a reviewed golden dataset of real label images with field-level boxes, transcription, package/category context, and expected rule outcomes. Track per-field precision/recall, OCR confidence calibration, review rate, false-compliance rate, and false-violation rate. Add CI gates for deterministic rules, report integrity, API auth, and frontend type/build checks.
14. Add a sticker/overprint alert as a human-review signal, not an automatic fraud decision. Test legitimate discount stickers, glare, package seams, and stickers not covering MRP to control false positives.

### P2: Extend the product where it already has an advantage

15. Improve the crawler and complaint bridge: join listing evidence to consumer receipt evidence, preserve product and seller history, compare listed price with declared MRP and transaction price, and support case correlation across marketplaces. Keep physical-label obligations separate from online-listing obligations.
16. Complete manufacturer-facing remediation and response workflows, localized citizen status updates, and bilingual (at least Hindi/English) end-to-end OCR/report coverage. Use a passport/QR only after identity binding, key management, and revocation rules are designed.
17. Add inspection-session exports and analytics only after the underlying findings, audit history, and rule versions are trustworthy. Those presentation capabilities already exist in part; decision integrity is the larger differentiator to build next.

## Final Position

SatyaDrishti’s strongest competitive position is **one connected consumer-to-enforcement platform with e-commerce surveillance**, not a claim that it has the most accurate OCR or legally certified metrology today. The latest pull strengthens OCR extraction and adds barcode decoding, but does not close the measurement, uncertainty, authorization, or audit-integrity gaps. The repository README is currently blank, so the source and this report should carry the project’s capability and limitation statements until that documentation is restored.

Prioritize calibrated measurement, uncertainty-aware verdicts, server-side access control, real evidence integrity, and reproducible evaluation. With those foundations, SatyaDrishti can combine the breadth peers are pursuing with the rigor their best implementations are beginning to demonstrate.
